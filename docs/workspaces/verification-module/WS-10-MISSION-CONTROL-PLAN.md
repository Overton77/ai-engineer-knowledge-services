# Mission Control verification dispatch plan

Coordinator preparation, 2026-09-05. Implementation is bounded to dispatching Knowledge Services capabilities; verification algorithms remain owned by Knowledge Services. The current Mission Control `executeStage` returns success without execution and cannot satisfy acceptance.

The first integration uses the reviewed public TypeScript client and strict request contracts produced by WS-08. Mission Control authenticates the caller and owns a durable workflow identity bound to tenant, mission, work item, attempt, idempotency key and request digest. Credentials, provider payloads and source bytes do not enter Temporal history. Authenticated ownership hints are validated by Knowledge Services before dispatch; the caller cannot choose a trusted verifier identity.

Temporal workflow code performs no network or database I/O. Activities submit a bounded versioned capability, observe authorized operation status and durable receipts, and reconcile uncertain submission using the same idempotency identity. Completed quality rejection is a terminal recorded outcome, not an infrastructure retry. Retryable transport/worker failures retain identity and use bounded retry/timeouts. Cancellation must reach the service operation and await or explicitly record reconciliation; cancellation before submission and during an uncertain response must not orphan accepted work.

The API supports authenticated launch, inspect, cancellation and controlled retry/reconciliation after the durable boundary exists. Readiness must reflect configured runtime availability. No route may report successful verification from the current placeholder activity or from a simulated port.

First tests use the installed Temporal1.8.1 development server on loopback7233, namespace verification-local, with preserved SQLite history. Worker processes are stopped after testing. Test the real public service on the same frozen fixture, duplicate submission, changed-payload rejection, quality failure, infrastructure retry, cancellation, worker loss/restart and history replay with `Worker.runReplayHistory`. Production remains Temporal Cloud and requires its separate authenticated connection proof; local success does not imply Cloud deployment.

For multi-tenant production, tenant-key Task Queue Fairness is recommended to prevent a large backlog from starving other tenants. It is a paid preview feature and remains an explicit deployment configuration decision; this local proof does not enable it or change account billing.

Ownership: WS-08 owner edits Knowledge Services service/client/API/worker. Coordinator owns Mission Control preparation and later integration review; no shared algorithm copy is introduced. Stable client propagation and cancellation contracts are the next dependency before finalizing the cross-repository adapter.
