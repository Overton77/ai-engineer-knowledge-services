# Completed benchmark reads

Coordinator implementation session, 2026-09-05/06. EV-068/069 establish actual completed benchmarks and local process recovery. EV-070 accepts compact authenticated reads after actual HTTP/built CLI/MCP HTTP execution and independent SQL/Storage/signature projection audit.

The service uses distinct benchmark IDs at `GET /v1/verification/benchmarks/{runId}` and its `/manifest` child. Typed methods are `getBenchmarkRun` and `getBenchmarkRunManifest`; CLI commands are `knowledge benchmark show` and `knowledge benchmark manifest` with an input containing only `runId`. MCP exposes `knowledge_get_benchmark_run` and `knowledge_get_benchmark_manifest` with tenant/correlation context and a run ID. No caller can supply a manifest, key or computed result.

API deployment configuration `VERIFICATION_BENCHMARK_READ_PUBLIC_KEYS_JSON` is a bounded array of `{keyId, publicKeyPem}` Ed25519 public keys. This trust configuration is independent of submission catalogs and never requires the worker's private signing key. Duplicate IDs, private keys, non-Ed25519 keys, unknown fields and excessive size are rejected at startup. Missing configuration leaves reads unavailable. A public key rotation may retain multiple explicitly trusted historical keys; an unknown signing identity fails integrity checks.

Each read creates fresh tenant authorization and resolver state. The repository first requires a sealed aggregate linked to a succeeded canonical benchmark operation and its correctly bound terminal step receipt. It hydrates the registered publication with exact byte checks, verifies the signature using deployment trust, and checks the aggregate, checkpoint plan, canonical dataset/experiment, arm/evaluation and timing bindings. Microsecond database times are compared in SQL; the signed manifest's canonical millisecond representation is compared separately. Merely sealed, running, cancelled and foreign-tenant results remain hidden. Corrupted visible state is an integrity failure, not a missing result.

Public schemas contain compact artifact references, run/operation/dataset/experiment/evaluation identities, explicit engineering limitations and bounded reproducibility metadata. They exclude storage locators, evidence/checkpoint/report bodies, signature material and keys. A verified signature establishes recorded provenance, not human-gold accuracy, assessed source authority or calibration.
