## Overview

The module verifies capture-bound assertions and fields. Authorized services acquire source bytes, register them in a tenant-scoped content-addressed store, parse them in a restricted container, admit canonical projections, resolve selectors and computations, and record judgments and policy results. API/MCP orchestration exists; verification-specific transport composition is still being built. User context requires separate producer/verifier deployments, immutable evidence, bounded semantic tools, and no patient-specific advice.

## Trust boundaries and assumptions

Protected assets are private captures, provider credentials, tenant-owned artifacts and runs, immutable parent/selector relationships, deployment identity, policy/benchmark versions, and bounded compute/spending. A source publisher may control HTML/PDF bytes and redirects. A tenant caller may submit its own inputs and identifiers, but does not gain another tenant's token, trusted parser image selection, database credentials, or host Docker access. A model response is untrusted data even if its provider transport succeeds.

The trusted service must authorize the tenant before hydrating source bytes and must bind runtime identities from authenticated deployment context. Library ports deliberately accept trusted adapters; supplying a forged in-process adapter already requires host authority and is not proof of a remote exploit. The low-level artifact store cannot independently infer the caller's identity. Content hashes provide integrity, not permission or factual correctness.

Existing local proofs establish restrictive Storage JWT policies, immutable relational records, parser isolation, and strict admission. They do not establish a remote deployment, cloud identity provisioning, every API endpoint, or physical tenant isolation. Generic audit replay currently checks registered projection bytes but does not invoke the parent-specific parser-admission service; that composition gate is recorded in ADMISSION-REVIEW.md. Semantics and provider admission remain under implementation and must not be inferred from this draft.

## Severity calibration

Critical would require demonstrated broad unauthenticated host/database control or cross-tenant privileged mutation. A malformed document that is rejected inside its bounded sandbox is not critical. High applies to a reachable authorization, source-derivation, internal-network, or provider-disclosure boundary failure with concrete prerequisites. Medium applies to bounded availability loss, partial-result state errors, or restricted operational leakage with established reachability. Low applies to narrow diagnostic or defense-in-depth defects without a demonstrated confidentiality/integrity/availability boundary crossing. Missing deployment evidence lowers confidence in reachability; it does not silently waive the required control.
