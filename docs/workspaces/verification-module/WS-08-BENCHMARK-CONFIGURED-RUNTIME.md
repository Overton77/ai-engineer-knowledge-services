# Registered offline benchmark runtime

Configured local submission/worker execution is accepted in EV-068; two actual process-recovery boundaries are accepted in EV-069, 2026-09-05. EV-067 covers internal publication.

The public submission is `POST /v1/verification/benchmarks:run`, `KnowledgeClient.runBenchmark`, `knowledge benchmark run`, or MCP `knowledge_run_benchmark`. Its strict request contains `verificationContractVersion: verification.v1`, a registered dataset artifact ID/digest, a registered experiment artifact ID/digest, and `executionMode: offline_recorded`. Authenticated tenant/actor and canonical attempt ownership follow the existing verification context resolver. Request bodies cannot create catalog grants, supply checkpoint plans/results, choose runtime identities, or authorize live provider calls.

`VERIFICATION_BENCHMARK_CONFIG_JSON` is trusted deployment configuration shared between API and worker. The strict `verification-benchmark-runtime.v1` document contains one tenant, `inputs`, `profiles`, `replays`, `sources`, `policies`, and `runtime`. Every input pair must have matching profile/replay/source grants under that tenant. Catalog constructors validate their own references and bounds. Runtime includes stable deployment/capability/code identity, git SHA, dirty state, and a same-tenant registered code snapshot when dirty. It omits attempt ID; the worker binds that from the authenticated canonical operation.

The API requires canonical ownership grants and the complete catalog configuration before admitting benchmark submissions. It denies unknown registered pairs before creating an operation. Configuration validation establishes catalog coverage; it does not attest to live artifact availability or remote worker health. The worker performs actual registration, byte-digest, source-import, profile, checkpoint and policy hydration before execution/publication.

The worker additionally requires `VERIFICATION_BENCHMARK_SIGNING_PRIVATE_KEY_PEM` and `VERIFICATION_BENCHMARK_SIGNING_KEY_ID`. The Ed25519 private key remains runtime secret material. The standalone benchmark handler creates no parser process or provider dispatch adapter. It uses existing admitted imported projections and recorded provider wire evidence, a durable complete checkpoint plan, retained start/completion timing, and the fenced per-arm publisher.

The canonical step is `replay_recorded_and_register`. Its result artifact is the signed benchmark publication manifest. Its compact output contains distinct benchmark/evaluation IDs, manifest digest, and explicit all-false human-gold/source-authority/calibration claims. CLI `--wait` reports completed benchmark execution with exit code0 and these claims; it does not synthesize a `qualityPassed` value. Verification operations retain their existing quality-dependent exits.

The worker's cancellation monitor performs non-overlapping canonical status reads and stops in `finally`. It propagates actual infrastructure polling failures as retryable rather than relabeling them as user cancellation. Live operation/lease checks gate durable checkpoints and publication. The normal canonical worker writes the terminal receipt after the handler completes.

Actual configured integration and two SIGKILL/higher-fence recovery proofs now pass; see EV-068/069 and the independent worker/recovery audit. Still required: benchmark public read projection and compare operations, failed-call admission/full retained pilot replay, cases/scores and human-gold/calibration/deployment gates. The MCP proof covers its adapter and real HTTP client; a separate real MCP HTTP session is not claimed.
