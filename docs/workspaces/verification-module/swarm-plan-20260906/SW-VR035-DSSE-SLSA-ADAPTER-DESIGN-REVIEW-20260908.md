# VR-035 DSSE/SLSA adapter design review — 2026-09-08

The proposed bounded adapter is conceptually compatible with the primary formats, with two required clarifications. SLSA v1.2 defines an in-toto Statement (`_type: https://in-toto.io/Statement/v1`) whose predicate type is `https://slsa.dev/provenance/v1`; the SLSA page says `buildType`, `builder.id`, `externalParameters`, and `resolvedDependencies` describe the trusted build platform and its inputs. DSSE signs the exact payload bytes using its Pre-Authentication Encoding (PAE), and the envelope carries `payloadType`, base64 `payload`, and one or more signatures. The adapter must therefore sign canonical UTF-8 statement bytes as the DSSE payload and verify the DSSE PAE, rather than signing the outer JSON envelope or a noncanonical object.

The minimal pure-core surface should be an optional export/import pair around the existing signed audit bundle:

- `createVerificationDsseSlsaAttestation(input)` first validates the existing signed audit bundle with a trusted verifier, then derives the statement subject from the canonical audit-bundle signable payload digest. The caller supplies only a signer and server-owned deployment metadata; builder ID, build type, parameters and dependencies are derived by the adapter.
- `inspectVerificationDsseSlsaAttestation(input)` requires the expected canonical audit bundle, trusted signer/builder policy and verifier. It validates DSSE envelope exact keys, payload type, base64/byte lengths, PAE signature, in-toto statement shape, the exact expected subject digest, and the fixed predicate type. It returns `verified` or a stable reason code.
- Existing Ed25519 audit-bundle sealing and operations remain unchanged; the new artifact is optional and additive.

The statement should use `_type: https://in-toto.io/Statement/v1`, `predicateType: https://slsa.dev/provenance/v1`, one subject whose SHA-256 digest is the canonical audit-bundle signable payload digest, and a SLSA predicate with a versioned documented `buildType`, a server-derived `builder.id` URI, public exact canonical manifest/policy digests in `externalParameters`, and input artifact handles represented as digest-only `resolvedDependencies` descriptors. Do not expose tenant/object keys or mutable caller claims. Do not claim a SLSA build level: SLSA says builder identity determines the trust base and consumers must enforce signer-builder pairs; this adapter can provide provenance format support without asserting a level.

The contract/public path needs one optional attestation artifact reference and a typed inspection result containing DSSE payload type, statement/predicate identifiers, subject digest, signer key ID, builder ID, and verification status/reason. The persistence path must register the immutable DSSE bytes with a media type and bind its parent to the signed audit bundle; the public audit inspection projection may expose only the typed digest/status metadata. Add focused tests for PAE/signature tampering, payload/base64/byte-length errors, subject or predicate substitution, builder/signer mismatch, private parameter injection, dependency substitution, and expected-bundle mismatch. A read-only offline CLI export/inspect command can exercise this pure path without provider or database calls.

Conceptual conclusion: **minimal adapter is viable**, but it must be an actual DSSE envelope carrying a standard in-toto/SLSA statement and must derive all trust-bearing fields. A custom JSON signature over a locally invented predicate would not satisfy the standard-format clause.
