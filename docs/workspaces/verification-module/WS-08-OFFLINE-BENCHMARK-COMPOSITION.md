# Registered offline benchmark composition

Coordinator implementation/review, 2026-09-05. This is a prerequisite for the durable `runBenchmark` operation, not public operation admission.

`RegisteredDiagnosticsOfflineBenchmark.prepare` owns the sequence of registered input admission, sealed diagnostics profile admission, tenant-owned source import/current native projection preparation, and successful retained-call replay. It accepts a public request plus trusted tenant/run identity; it has no provider dispatch port. The configured experiment must exactly match all four sealed diagnostics arm definitions. Its executor binds run ID, dataset, full case and arm values, repetition bounds and offline network policy. Every case must have a complete projection matrix with exact evidence identities before an executor is returned. Missing replayed observations remain explicit provider-unavailable abstentions; they do not become successful semantic observations.

The executor passes `offline_replay` to the existing recorded-arm composer. Original observations remain immutable. Reused call attributions retain their historical cost-state classification, but carry no new reservation, fresh latency or additional actual charge. Unknown original costs remain unknown; this does not reconcile the held WS-07 liabilities. Source authority remains unassessed, and this implementation cannot establish human gold or clinical correctness.

The runner now accepts an optional lifecycle with retained original `startedAt` and an atomic `complete()` callback. It verifies canonical timestamps, checkpoint times within the run, and cancellation after completion awaits. The four new lifecycle tests establish an identical run manifest after interruption/resume with a changed clock, plus denial on lease-loss, cancellation and backward completion time. A shared `createVerificationBenchmarkCheckpointPlan` supplies the exact case/arm/repetition/context-digest matrix to both the runner and forthcoming persistence adapter. Existing callers without a lifecycle preserve their behavior.

The real local Postgres/private Storage proof authenticates the existing 98 profile files, 82 source copies and three retained `tru-sites-source` provider checkpoints, then executes the complete 43-case/four-arm matrix. It is deliberately only a three-observation replay input: missing observations for other cases remain abstentions. Its 172 results are not a fresh full pilot. The proof uses memory checkpoints and a fixed lifecycle time, so it does not establish crash recovery or database fencing.

## Durable state and canonical publication

The delegated persistence slice will retain immutable checkpoint JSON under the canonical operation lease/fence and the exact expected matrix. CAS export can follow; it must not substitute an unfenced file write for durable execution state. Completion retains its first timestamp only when the entire expected matrix exists. Publication remains separate from execution completion.

The existing verification-v1 `evaluation.eval_run` contract represents one experiment arm and requires terminal artifact bindings. It must not be made into a fake aggregate arm or inserted with a null verification contract to evade that shape. The intended publication mapping is one canonical `eval_run` per real `experiment_arm`, linked from the aggregate benchmark lifecycle by an explicit relation. A shared aggregate manifest is possible only with exact run/arm and dataset/experiment binding. The current checkpoint adapter should not invent those publication records. Registered benchmark manifest sealing, per-arm canonical evaluation records, operation terminal publication, worker integration, API/client/CLI/MCP and real process recovery remain required work.
